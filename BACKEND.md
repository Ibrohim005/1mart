# Инструкция для бэкенд-разработчика — Paylov Market

> Витрина маркетплейса Paylov (АО «Octagram»). Основа — фронтенд Zoo Market, переделанный
> под Paylov: общий каталог товаров, **только B2B**. Компания платит **с баланса на сайте**,
> который пополняет переводом со своего расчётного счёта на реквизиты площадки, или
> **корпоративной картой**. Личных карт, наличных, рассрочки, аукционов и объявлений
> **нет**. См. раздел «Баланс компании (B2B)». Эталон контрактов — моки в `layers/api-mock/server/api/**` и типы в
> `apps/host/shared/types/*`: что отдаёт мок, то и ждёт фронт.

Фронтенд собран и работает на моках. Чтобы подключить реальный API, нужно реализовать
эндпоинты ниже и выставить переменную окружения:

```bash
NUXT_PUBLIC_API_BASE=https://api.paylov.uz/api npm run build
```

После этого из `apps/host/nuxt.config.ts` убирается строка `'../../layers/api-mock'`
из `extends` — слой моков больше не нужен. Код страниц и компонентов не меняется.

## Общие соглашения

**Конверт ответа.** Все эндпоинты возвращают одну структуру:

```ts
interface ApiResponse<T> {
  payload: T | null
  errors: Array<{ code: string, message: string, field?: string }> | null
  timestamp: string   // ISO
  trace?: string      // сквозной идентификатор запроса
}
```

При ошибке: `payload: null`, заполненный `errors`, HTTP-код по существу ошибки.
Фронт разворачивает конверт в `layers/shared/app/composables/useApi.ts` и бросает
исключение с `statusMessage` из первой ошибки.

**Деньги** — целые тийины, не дробные суммы:

```ts
interface Money { amount: number, currency: 'UZS' }   // 699 990 сум → { amount: 69999000 }
```

Округление только при выводе. Это исключает ошибки округления при скидках и рассрочке.

**Заголовки запроса** (ставятся автоматически):

| Заголовок | Значение | Зачем |
|---|---|---|
| `x-install-id` | UUID устройства из cookie `zoo_install_id` | привязка гостевой корзины |
| `accept-language` | `ru` / `uz` | язык контента |

При входе пользователя гостевую корзину нужно смержить с пользовательской по `x-install-id`.

Идентификатор лежит в cookie, а не в localStorage: страницы корзины и
оформления рисуются на сервере, и из localStorage сервер его не прочитает —
SSR отдавал бы чужое содержимое, а на гидратации оно подменялось бы.
Мок уже разводит состояние по этому идентификатору: две вкладки в разных
браузерах видят разные корзины и разное избранное.

## Эндпоинты

### Каталог

| Метод | Путь | Ответ | Где используется |
|---|---|---|---|
| GET | `/categories/root` | `Category[]` | лента категорий на главной, меню «Категории» |
| GET | `/banners` | `Banner[]` | баннер главной, промо-ряды |
| GET | `/products/shelf?kind=discounts\|recommended\|wow&limit=N` | `ProductCard[]` | полки на всех страницах |
| GET | `/search?q&categorySlug&sort&page&perPage&exact&<фильтры>` | `SearchResult` | категория, поиск |
| GET | `/search/suggestions?q` | `ProductCard[]` | подсказки в строке поиска |
| GET | `/products/{slug}` | `Product` | карточка товара |

`sort` принимает: `popular` (по умолчанию), `priceAsc`, `priceDesc`, `rating`, `new`.
Фильтры приходят как `?brand=apple,samsung&color=black&memory=128&country=china&price_from=100000&price_to=900000`. Набор фильтров зависит от категории (см. `CATEGORY_FACETS` в `layers/api-mock/mocks/facets.ts`); подписи значений — на языке из `accept-language`.

**Поиск прощает опечатки.** В моке это расстояние Дамерау — Левенштейна
(`layers/api-mock/server/utils/fuzzy.ts`); бэкенд волен заменить его
полнотекстовым индексом — контракт держится на двух полях `SearchResult`:

| Поле | Когда приходит | Что делает фронт |
|---|---|---|
| `correctedTo` | запрос исправлен автоматически (например, забытая раскладка `,sr` → `бык`) | над выдачей строка «Показываем результаты по запросу …» и ссылка «Искать …» с `?exact=1` |
| `suggestion` | выдача пуста, но есть близкое слово | в пустом состоянии «Возможно, вы искали …» |

`?exact=1` означает «искать ровно как набрано»: никаких исправлений,
пустая выдача — это ответ. Подсказки строки поиска должны прощать те же
опечатки, иначе они пропадают там, где сам поиск товары находит.

**Важно про кэширование.** Тяжёлая часть карточки товара (`/products/{slug}`) кэшируется
на CDN 10 минут. Цену и остаток нужно отдавать отдельным некэшируемым эндпоинтом,
иначе карточку нельзя кэшировать вообще:

```
GET /products/{slug}/price  →  { price: Money, fullPrice: Money | null, available: number }
```

### Оформление заказа

| Метод | Путь | Тело / ответ |
|---|---|---|
| GET | `/checkout/addresses` | `Address[]` |
| POST | `/checkout/addresses` | `Address` |
| GET | `/checkout/cards` | сохранённые карты |
| POST | `/checkout/cards` | `{ number, expiry }` |
| GET | `/checkout/promocodes` | `Promo[]` — `{ id, code, description, percent, freeDelivery?, until }` |
| POST | `/checkout/quote` | `{ paymentMethod, cardId, deliveryType, provider, pickupPointId, addressId, promoCode }` → расчёт заказа, см. ниже |
| POST | `/checkout/otp` | то же тело → `{ status: 'sent', otpId, expiresIn: 59, attemptsLeft, phone }` или `{ status: 'locked', lockedUntil }` |
| POST | `/checkout/otp/verify` | `{ otpId, code }` → `{ status: 'ok', token }` / `{ status: 'wrong', attemptsLeft }` / `{ status: 'expired' }` / `{ status: 'locked', lockedUntil }` |
| POST | `/checkout/promocodes` | `{ code }` |
| POST | `/orders` | `CheckoutDraft` → `Order` |

Состояния оплаты, которые уже отрисованы на фронте: успех, ожидание, ошибка.
Ответ на `POST /orders` должен различать их — например, полем `status`.

Фронт уже отправляет заказ и разводит ответ по трём экранам:

```
POST /orders  { paymentMethod, cardId, deliveryType, provider, pickupPointId, addressId, promoCode, otpToken }
  → 200 { status: 'placed', orders: [{ id, number, amount }], transactionId, reserved, paymentStatus: 'held', receipt }
        → «Заказ оформлен, средства зарезервированы», корзина очищена
  → 200 { status: 'outOfStock', items } → А1: подсветить позиции, предложить убрать
  → 200 { status: 'insufficientFunds', required } → А3: выбрать другую карту
  → 403 otp_required                    → без токена подтверждённого кода заказ не создаётся
                                          (токен привязан к сумме и карте, одноразовый)
```

Полный поток оплаты (ТЗ Paylov, UC-FL-10, п.4.1.6.10–11) — см. раздел «Оплата и статусы заказа Paylov» ниже.

Кнопка оплаты блокируется на время запроса — повторный клик не создаёт второй
заказ. Со стороны бэкенда всё равно нужен ключ идемпотентности: фронт готов
присылать его заголовком, если он будет в контракте.

### Авторизация

| Метод | Путь | Тело |
|---|---|---|
| POST | `/auth/phone` | `{ phone }` → `OtpChallenge` |
| POST | `/auth/verify` | `{ phone, code }` → `AuthSession` |
| POST | `/auth/token/refresh` | `{ refreshToken }` |
| POST | `/auth/logout` | — |
| POST | `/auth/password/request` | `{ phone }` → `{ sent, resendAfter }` |
| POST | `/auth/password/confirm` | `{ phone, code, password }` → `AuthSession` |

Вход по телефону с кодом из SMS — экран ввода кода уже собран (5 ячеек).

**Восстановление пароля.** Сценарий собран целиком: «Забыли пароль?» во входе →
номер → тот же экран кода → новый пароль с повтором. Ожидания от ответов:

- `POST /auth/password/request` на незарегистрированный номер отвечает `404` —
  фронт по этой ошибке уводит человека в регистрацию, а не оставляет в тупике;
- `resendAfter` задаёт таймер повторной отправки (сейчас 90 секунд);
- `POST /auth/password/confirm` на протухший или неверный код отвечает `422` —
  фронт возвращает к вводу кода;
- успешный ответ сразу открывает сеанс: повторного входа фронт не просит.

но в моках по ним нет данных — фильтрацию делает бэкенд.

### Личные данные покупателя

Адреса, карты и получатель больше не лежат в разметке страниц — фронт берёт
их с сервера. Подмените три эндпоинта, и корзина с оформлением заработают
на настоящих данных:

| Метод и путь | Что отдаёт |
| --- | --- |
| `GET /user/addresses` | `[{ id, title, subtitle }]` — сохранённые адреса доставки |
| `GET /user/cards` | `[{ id, title, subtitle }]` — привязанные карты, номер уже замаскирован |
| `GET /user/profile` | `{ name, phone }` — получатель в оформлении заказа |

Полный номер карты на фронт не отдаётся ни в каком виде.

### Баннеры — готовые картинки

`GET /banners` отдаёт баннер цельной картинкой: весь текст, цены и плашка срока
впечатаны в макет. Поля:

| Поле | Зачем |
| --- | --- |
| `image` | картинка для большой карусели, 1240×345 |
| `imageSmall` | она же для ряда промо-баннеров, 529×214 |
| `link` | куда ведёт баннер целиком |
| `title` | идёт в `alt` картинки |
| `description` | скрытый текст для поисковика и скринридера |

Картинки нужны **на каждый язык**: текст внутри них не переводится. Сейчас в
моках лежит выгрузка из Figma с узбекским текстом, поэтому на русской локали
баннер показывает узбекские слова — нужны русские версии макетов.

Старые поля (`title`, `oldPrice`, `price`, `discountLabel`, `until`, `tone`)
остались: если `image` пустой, фронт соберёт баннер из них текстом, как раньше.

### Зоотовары

В моках 15 товаров — по 5 в «Кормах», «Аксессуарах» и «Лекарствах». У них своя
форма описания: вместо породы, масти и пола — состав, вес упаковки, срок
годности, действующее вещество, рецепт, размер, материал, гарантия. Выбор
вариантов (`optionGroups`) у товара пустой, видео нет, остаток 24.

Фотографии товаров временно берутся от категорий — настоящие снимки ждём
вместе с каталогом.

### Локализация ответов

Весь текст интерфейса уже вынесен в `apps/host/i18n/locales/{ru,uz}.json` —
фронт переводит его сам. Но текст, который **приходит из API**, фронт не переводит:

| Что | Где видно |
| --- | --- |
| Названия категорий и товаров | каталог, карточка, крошки |
| Имена и описания продавцов | карточка продавца, корзина |
| Бейджи (`НОВИНКА`, `СТАЛО ДЕШЕВЛЕ`) | карточки товара |
| Статусы заказа и транзакций | кабинет |
| Характеристики: названия и значения | карточка товара |
| Подписи способов оплаты и доставки | оформление |

Ожидаем, что ответ зависит от заголовка `accept-language: ru | uz` — фронт его
уже шлёт. В моках так сделаны баннеры (`GET /banners`), остальное пока
отдаётся только по-русски.

## Оформление заказа: расчёт

**Итог считает сервер**, страница только показывает пришедшее:

```
POST /checkout/quote  { paymentMethod, cardId, deliveryType, provider, pickupPointId, addressId, promoCode }
  → { goods, promoCode, promoPercent, promoAmount, deliveryType, provider, pickupPointId,
      delivery, commission, payable, eta,
      couriers: [{ id: 'express24'|'maxsus'|'yandex', price, days, eta }],
      pickupPoints: [...], stockIssues: [...] }
```

Запрос повторяется при смене промокода, способа и службы доставки. Все суммы — целые тийины.
Комиссия (`commission`) показывается строкой «Комиссия», сейчас 0.

## Баланс компании (B2B)

Новые эндпоинты, контракт — моки в `layers/api-mock/server/api/balance/` и типы `BalanceOverview`, `BankDetails`:

| Метод | Путь | Что делает |
|---|---|---|
| GET | `/balance` | `{ available, reserved, company, requisites, invoices, operations, demo }`. В бою `demo: false` |
| POST | `/balance/invoices` | `{ amount }` в тийинах → счёт `{ id, number, amount, status, createdAt }` |
| PATCH | `/user/company` | реквизиты покупателя: `{ name, inn, bank, mfo, account }`, ИНН 9 цифр, МФО 5, счёт 20 |

- `POST /balance/invoices/:id/credit` есть только в моке. В бою счёт закрывает банковская выписка: сверка по номеру счёта в назначении платежа и по счёту плательщика.
- В `/checkout/*` и `POST /orders` приходит `paymentMethod: 'balance' | 'card'`. При `balance` `cardId` равен `null`, SMS-код не нужен. Если денег мало, ответ `{ status: 'insufficientBalance', required, available }`.
- При оформлении сумма резервируется. После подтверждения продавцом она уходит на его расчётный счёт, при отказе или отмене возвращается тем же способом.
- Реквизиты в моке (`PLATFORM_REQUISITES`) — заглушка. Настоящие должны приходить с бэкенда.

## Оплата и статусы заказа Paylov

1. «Оплатить» → окно-предупреждение «операцию выполняю я сам, без указаний третьих лиц» (п.4.1.6.11 п.9) — только на фронте.
2. `POST /checkout/otp` — код по SMS: **6 символов A-Z a-z 0-9, живёт 59 с, 3 неверных ввода → блок на 15 минут** (п.4.1.6.10). Мок возвращает `testCode` только для демо — **в бою его быть не должно**.
3. `POST /checkout/otp/verify` → `token`, затем `POST /orders` с `otpToken`.
4. Деньги **резервируются** на карте (`paymentStatus: 'held'`), заказ уходит продавцу → `awaitingSeller`.
5. Продавец подтверждает → списание (`charged`), `confirmed` → `handedToDelivery` (трек-номер, служба) → `delivered` (самовывоз: `readyForPickup`).
6. Продавец отклонил → `rejectedBySeller`, резерв снят (`refunded`). Покупатель отменил до подтверждения → `canceled`.
7. После доставки: возврат (`returnRequested`) и отзыв.

Статусы — `OrderStatus` и `PaymentStatus` в `apps/host/shared/types/order.ts`, подписи — `layers/api-mock/server/utils/orders-view.ts`.
В моке статусы двигаются по таймеру (≈20 / 40 / 65 с), в бою — по событиям продавца и службы доставки (вебхуки).

Демо-сценарии моков: карта Visa •0005 — нехватка средств; позиция с количеством ≥ 3 — нет в наличии; количество ровно 2 — продавец отклоняет.

**Адрес с картой.** Карта настоящая — Leaflet с тайлами OpenStreetMap.
Точка ставится кликом или перетаскиванием метки, кнопка со стрелкой определяет
местоположение через `navigator.geolocation`. Форма отдаёт наверх
`{ lat, lng, flat, entrance, floor, intercom, comment }` — это тело для
`POST /user/addresses`. Новый адрес сразу становится выбранным на оформлении,
пока только в состоянии страницы: список адресов нужно сохранять на сервере
(`GET /user/addresses`, `POST /user/addresses`) и возвращать `id` созданного.

Если тайлы будут отдаваться со своего домена или другого провайдера, его нужно
добавить в `img-src` политики безопасности (сейчас там `tile.openstreetmap.org`).

**Догрузка выдачи.** Пагинации в макете нет, поэтому каталог и поиск
запрашивают растущий `perPage` при `page=1`: первый экран — 6 карточек
в каталоге и 24 в поиске, кнопка «Показать ещё» прибавляет столько же.
Бэкенду достаточно честно отдавать `total` — по нему фронт решает,
показывать кнопку или нет. Если появится курсорная пагинация, контракт
поменяется на `cursor`, и это единственное место, которое придётся править.

**Отмена удаления.** Удаление строки корзины не спрашивает подтверждения —
вместо этого подтверждение живёт 6 секунд и даёт «Вернуть», которое повторяет
`POST /cart/items { skuId, quantity }` с прежним количеством. Если сервер
начнёт удалять строки физически, нужен либо мягкий delete, либо окно
на восстановление.

**Избранное из корзины.** Сердце и корзина — разные действия:
`POST /favorites { productId }` + `DELETE /cart/items` против просто `DELETE /cart/items`.
